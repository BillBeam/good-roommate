# 故障处理表

试跑期间机器出问题时，按这张表判断、照表执行。只有表里没有的情况才停下来问。

几条不变的规矩：

- **不打断正在跑的任务。** 没有任务在跑时，为修复而重启或换机按本表执行。
- **一台机器只重启一次。**
- **同一时间最多一台实例**，单价不超过 25 元/时。
- **预算上限不变**：显卡费到 235 元停下收尾（卡里的 250 元留 15 元缓冲）；DeepSeek 不超过 60 元。
- 本表里的"中转"指 [`ops/train_relay.py`](../../ops/train_relay.py)，"会话"指发中转请求的这一边。
- 中转每轮结束都会在 PR 里留评论。连不上时，评论开头写"连不上"，并写明按本表判出的情况。

## 判断"坏了"用什么证据

只靠 SSH 连不上，不能判机器坏了。做镜像那次（2026-10-26 17:45–17:52）SSH 断着，机器和任务其实都好好的。判断"坏了"要有不经 SSH 的证据：

| 信号 | 从哪来 | 说明 |
|---|---|---|
| 实例状态 | 平台接口 `DescribeCompShareInstance` 的 `State` | Running / Stopped / ImageMaking / Starting / Rebooting 等 |
| GPU 利用率等监控 | 平台接口 `GetCompShareInstanceMonitor`（时间序列），以及 `DescribeCompShareInstance` 的 `MonitorMessages`（最近一次快照） | 中转取最近 20 分钟的数据（`health_signals`）。名字里带 gpu 和 util/usage 的指标算作 GPU 利用率 |
| 主线预计什么时候跑完 | 数据分支 `runs/m2pilot/relay/mainline.json` | 会话起主线时给出预计时长；中转看到主线结束时记下结束 |
| 机器自己的记录 | 记录仪 `out/diag/netwatch.jsonl`（每分钟一行） | 连不上的时候取不回来；重新连上后的第一次连接会取回，作为事后证据 |

平台接口实际返回哪些指标，由中转的 `signals` 动作查出来，写进数据分支 `runs/m2pilot/relay/signals.json`。

## 表

| # | 情况 | 判断依据 | 动作 |
|---|---|---|---|
| 1a | SSH 连不上，机器在干活 | 每次连接 15 秒超时，共试 3 次，都在建连阶段失败。实例状态是 Running，且最近 20 分钟 GPU 利用率最高到过 5% 以上 | 只是看不见：中转照常把兜底关机续到 2 小时后，不重启，不换机。会话每轮（不超过 2 小时）再看一次 |

| 1c | SSH 连不上，证据显示没在干活 | 实例 Running，最近 20 分钟 GPU 利用率一直低于 5%；或者拿不到 GPU 信号，且已过主线预计结束时间 | 视为坏了，且没有任务在干活。中转把兜底关机缩到 30 分钟，会话照表处理：这台没重启过，就重启一次；重启后的第一次连接要取回记录仪日志和 diag。重启后仍连不上，或显卡不可见，就按第 7 行换机 |

| 3b | 实例停了 | 状态 Stopped：兜底关机到点，或平台停机 | 会话起机器（`start`）。起不来（比如没有库存），按第 7 行换机 |
